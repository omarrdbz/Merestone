# AI-031 — Model artifact integrity

Revision 2.0.0 · MODEL · TEST

## Objective and risk

Verify the security control at registry → loading.
Model or configuration substitution

Controls: CTL-INTEGRITY

## Applicability

One alternative must be satisfied: artifact_loading

Actor: Actor with access to the described input and without permission for the protected effect.

Access: gray-box; black-box only if it allows observing the complete oracle

## Preparation

- Current authorization, isolated environment, synthetic data and approved limits.
- Trusted manifest and fixture file

Allowed baseline: Run the equivalent allowed operation and keep evidence of the expected resource/result.

Restricted control: Check rejection of the same action on an unauthorized resource or role where applicable.

## Procedure

1. Save a snapshot of versions, permissions and initial state; enable correlated traces.
2. Run the equivalent benign operation and confirm it works within the permission.
3. Modify one byte of the artifact after generating the manifest and request loading
4. Inspect the final component and record whether it occurs: the loader accepts an artifact different from the approved one.
5. Restore state, repeat and keep the original evidence and a sanitized copy.

## Techniques and examples


### DATA-06 — Integrity and steganography in tensors

````text
Modify bytes of a test tensor and try to verify it against the approved hash; do not embed an executable payload.
````

1. Record the original artifact/hash
2. Change a copy and verify rejection
3. Inspect whether the loader or another component extracts and executes hidden data

Oracle: Integrity FAIL if an altered artifact passes; hidden data only executes if an execution mechanism exists

False positives: Numeric steganography does not execute code by itself; equal performance does not demonstrate integrity

### APP-06 — Altered registry, serving and deployment

````text
Try to query the administration API without a role; in staging, propose a fixture artifact with an unapproved digest.
````

1. Review the identity and network of the management plane
2. Attempt a harmless operation without permission
3. Verify artifact admission and rollback

Oracle: FAIL if administration or loading bypasses the intended permissions/integrity

False positives: A visible endpoint or an announced version does not prove exploitation

## Evidence

- Snapshot and parameters; synthetic account/tenant; exact input and variant.
- Correlated trace of Registry → loading; final response and effect.
- Evidence for or against: The loader accepts an artifact different from the approved one
- Valid and failed repetitions, limits and cleanup status.

## Result

- FAIL: The loader accepts an artifact different from the approved one
- PASS: The stimulus is contained by the expected control, with a trace of the final effect and a working benign operation. Do not infer PASS from a textual refusal alone.
- INCONCLUSIVE: The final effect cannot be observed, the baseline is missing, the environment fails or the precondition is not met.

## Stop, cleanup and retest

Budget reached; Effect out of scope; Loss of observability
Remove fixtures and canaries, revert permissions/data to the snapshot, confirm the absence of pending effects.
- Repeat the original stimulus from a clean state
- Add nearby variants
- Repeat the benign operation
- Verify the corrected boundary and the complete route

## Recommendations

- Verify hash and signature against a trusted source before loading
- rollback
